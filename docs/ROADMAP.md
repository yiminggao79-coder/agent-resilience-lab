# 后续方向

按"缺口 → 具体做法 → 验收方式"记，不写愿景。

## 1. 真实外部仓库的构建链路

**缺口**：现在的 Coding 证据集中在 stdlib Python。普通工程依赖 `npm` / `make` / 编译工具链，这套运行时还没接进去。

**做法**：从一个具体的 toolchain 开始，显式注册宿主可执行文件与它们的资源 scope，把"安装依赖"和"运行构建"分别做成一类受管命令，而不是放开一个 shell。

**验收**：真实项目上完成"失败 → 修 → 构建与测试通过"，每一步都有审批摘要与效果确认；失败的中间态如实保留。不承诺一次覆盖 npm/make/PTY。

## 2. 长任务收敛

**缺口**：冻结验收里第一个项目末轮用了 48/50 次请求，存在真实的重复检查成本。

**做法**：先对已消费的 Trace 做有限归因（哪些重复是有效的验证、哪些是无效的复读），再谈通用的规划或监督机制。

**验收**：同一任务上请求数下降且外部检查不退化；旧成绩不重判，新版用新冻结题。

## 3. 跨平台执行后端

**缺口**：原生沙箱只有 macOS。Linux 缺等价 backend，Windows 缺 POSIX 运行时接口。

**做法**：Linux 先用 namespace/cgroup 做一层最小可用隔离，接口与 macOS backend 对齐；Windows 明确标注不支持，而不是降级成"裸跑但加个提示"。

**验收**：同一批故障注入用例在两个平台上有等价结论；不可用时仍能干净拒绝。

## 4. 状态规模

**缺口**：SQLite 全状态归档 + 字节启发式在千轮对话上的表现未验证。

**做法**：先做可复现的长会话基准（轮数、工具调用数、上下文压缩次数固定），再决定是分区、是索引、还是改数据结构。

**验收**：给出 p50/p95 的写入与恢复耗时曲线，而不是一句"性能良好"。

## 暂不做

并行工具调度、完整 TUI、多模态、分布式会话、插件市场、OAuth 生态。这些要么与"每一步可解释"的目标冲突，要么需要先在 1–3 上拿到证据。
