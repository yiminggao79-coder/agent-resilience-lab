# MCP 与外部扩展

MCP 在这个系统里的定位很明确：**显式配置的受信外部边界**，不是命令沙箱的一部分，也不是自动发现的能力来源。

## 注册与发现

`registry.MCPToolRegistry` 只接受宿主显式配置的 server。进入 registry 时完成握手与分页发现，合成工具 schema 与身份 manifest：

- server 身份变化 → 拒绝续跑该 server 的历史调用；
- 工具 schema 变化 → 需要重新确认，不沿用旧审批；
- 不自动扫描本地进程、不读其他软件的配置、不连未声明的地址。

## 传输

| 传输 | 实现 | 状态 |
|---|---|---|
| stdio | `mcp.py`，JSON-RPC over pipes | 有真实 LLM 使用过的任务 |
| Streamable HTTP | `mcp_http.py`，协商 `2025-11-25` / `2025-06-18` | 有限实现；第三方 server、OAuth、重连、订阅、2026 discovery 未实现 |

官方 filesystem server 2.2.0 与官方 SDK 2.4.0 做过实际互操作（16 个工具与资源），这是"本地实际工具验证"，不是生态兼容性认证。

## 资源

按 server 暴露 `list / templates / read`。二进制只返回校验后的类型、长度与 hash，不把原始字节塞进上下文。

## 取消与重放

- 取消一次等待**不等于**远端已经静止：可能已经执行、可能正在执行、可能已计费。
- 因此外部效果一旦进入"未知"，一律 `needs_confirmation`，不自动重放。
- 已验证：外部效果发生但响应丢失时，跨新 CLI 进程不会重放该调用。
- 批准之后源文件发生变更，不会改变已批准的执行字节。

## 信任模型

MCP server 由操作者自己信任。它能做的事情超出命令沙箱的保护范围——这一点在文档里从不含糊。read-only 保护模式不允许启用无法约束的 MCP。

Skills 与 `AGENTS.md` 走同一条分层逻辑：内容进入上下文，脚本走审批与沙箱，加载不等于执行，规则不授予权限。
